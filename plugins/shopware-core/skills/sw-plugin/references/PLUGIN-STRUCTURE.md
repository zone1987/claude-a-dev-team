## Two files that are not in the tree, and do not belong there

| File | Why not |
|---|---|
| `CONTEXT.md` | exists during development, listed in `.gitignore` |
| `sbom.json` | generated, not committed |

## Not every plugin needs every entry

A plugin without an administration has no `app/administration/`; one without storefront
JavaScript has no storefront Jest. What a plugin has follows from what it contains — not
from what the template provides.

What **every** plugin has: `composer.json`, `CLAUDE.md`, `LICENSE`, `README.md`, `adr/`,
`tests/` and the tool configurations in the root.

## The five entries that need an explanation

| Entry | Why |
|---|---|
| `/composer.lock` | A plugin is a library, not an application. The lock file belongs to the project that installs it — otherwise the plugin forces its development dependencies onto the shop |
| `/src/Resources/public/**/*.map` | Source maps carry the complete source a second time. `shopware-cli` writes them only with `GENERATE_SOURCEMAPS=true` |
| `!/docs/mutation/` | An **exception** to the `/var/` logic: the baselines are committed, the verbose reports below them are not |
| `/sbom.json` | produced per release and attached to the artefact |
| `/CONTEXT.md` | the working notes; what survives them moves into an ADR, `CLAUDE.md` or `CHANGELOG.md` |

**`/src/Resources/public/` itself is committed** when the plugin ships through a Composer
registry: the target shop does not build the assets itself.

→ composer.json in full: [PLUGIN-COMPOSER.md](PLUGIN-COMPOSER.md)
→ The `Package` attribute under `src/Framework/Log/`: [PLUGIN-PACKAGE-ATTRIBUTE.md](PLUGIN-PACKAGE-ATTRIBUTE.md)
