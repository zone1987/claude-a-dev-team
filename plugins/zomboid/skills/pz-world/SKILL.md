# Project Zomboid world model

The world is a grid. A position is `x, y, z` where **x and y are square coordinates** and **z is the
floor level**, 0 being ground. Squares group into chunks, chunks into cells, and cells are what the
game streams from disk as players move.

**The constraint that governs every world task: only loaded parts of the world exist in memory.** A
square in an unloaded chunk is not a square with no objects — it is `nil`. The game loads chunks
around connected players, so on a dedicated server the reachable world is "wherever players are", not
the map. Any feature that wants to search the whole map has to be designed around that, and a query
returning nothing may be correct rather than broken.

## The spatial hierarchy

`IsoWorld` holds the metagrid and the current cell; `IsoCell` holds chunks; `IsoChunk` holds squares;
`IsoGridSquare` holds objects; an `IsoObject` may carry an `ItemContainer` holding items. Every level
has accessors in both directions, and `pz-java-api` carries their exact signatures —
`zombie.iso` alone is 454 types and 8,995 members.

Buildings and rooms are a second, overlapping structure: `BuildingDef` and `RoomDef` come from the
map data and exist whether or not the chunk is loaded, while `IsoBuilding` and `IsoRoom` are the live
objects. That distinction is what makes some building queries possible on unloaded map.

## World objects are tiles

Every static thing — a wall, a door, a fridge, a tree — is a tile with properties, and reading those
properties is how a mod decides what an object is:

```lua
local sq = getCell():getGridSquare(x, y, z)
if sq then
    for i = 0, sq:getObjects():size() - 1 do
        local obj = sq:getObjects():get(i)
        local props = obj:getProperties()
        if props:Is("container") then
            local c = obj:getContainer()
            -- c:getItems() holds the items on this square
        end
    end
end
```

`props:Is("name")` tests a flag, `props:Val("name")` reads a value. Which names exist is not a matter
of guesswork — the tile reference below enumerates all 230.

## Finding a thing by position

The practical pattern, and its limits:

1. **Given a coordinate**, `getCell():getGridSquare(x, y, z)` yields the square or `nil` if unloaded.
2. **Given a player**, `player:getSquare()` and then walk outward in rings of increasing radius.
3. **For items**, walk each square's objects, take each container, and scan its items by type.
4. **Stop at the loaded boundary.** A ring search that leaves the loaded area returns `nil` squares,
   which is the signal to stop rather than an error.

So "the nearest shovel to this player" is answerable within the loaded radius, and "the nearest
shovel on the map" is not answerable from live world state. If a whole-map answer is required, the
data has to come from the map files on disk rather than from memory — a different mechanism with
different guarantees.
