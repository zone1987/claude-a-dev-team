# Project Zomboid mod structure

A mod is a directory containing `mod.info` and a `media/` tree that mirrors the game's own. The game
loads `media/lua`, `media/scripts` and the rest from every enabled mod after loading its own, so a
mod adds to the game by placing files at the same paths.

## The minimum that loads

```
MyMod/
  mod.info
  poster.png
  media/
    lua/
      client/    -- UI, input; never runs on a dedicated server
      server/    -- authority, world writes; never runs on a client
      shared/    -- definitions both sides need
    scripts/     -- items, recipes, vehicles
```

```ini
id=MyMod
name=My Mod
description=What it does.
poster=poster.png
versionMin=42.0
```

`id` is the identity — the folder name and the id should match, and other mods reference it in
`require`. `versionMin` is what gates the mod to a build.

**The versioned layout is optional.** Build 42 added `common/` plus numeric directories such as `42/`
or `42.19/` beside `media/`, but a mod shipping `media/` alone loads in build 42 — most surveyed
build 42 mods do exactly that. Reach for the versioned form only when one package must serve build 41
and 42 together.

## Where things live on this machine

- **The game**: `~/Library/Application Support/Steam/steamapps/common/ProjectZomboid/Project Zomboid.app/Contents/Java`
- **Your data, mods, saves and logs**: `~/Zomboid` — including `console.txt`, `Logs/` and `Lua/`
- **Subscribed Workshop mods**: `~/Library/Application Support/Steam/steamapps/workshop/content/108600`
- **The official mod template**: `Workshop/ModTemplate` inside the install. It is the authoritative
  example of the packaging layout, including `workshop.txt`.
- **A dedicated server** runs from the same install via its `StartServer.command` script, so a local
  server for testing needs no separate download.

Reading a subscribed mod is the fastest way to settle a structural question: 33 of them are on this
machine, and they demonstrably load.

## Load order

Files load alphabetically within each directory, and `shared/` before `client/` and `server/`. A file
depending on another must sort after it or pull it in with `require`. When two mods define the same
thing, the later loader wins — that is a fact to design around rather than rely on, since enable
order is the user's choice.

For a script definition, reusing an existing id **replaces** that definition rather than merging with
it. That is how a mod overrides a base-game item, and also how two mods silently break each other.

## Publishing

`workshop.txt` beside a `Contents/` directory carries the Workshop metadata — `version`, `title`,
repeated `description` lines, `tags`, `visibility`. The template in the install shows the exact
nesting the uploader expects, which is `Contents/mods/<ModId>/`, not the mod directory directly.
