# Extraction strategy

What a script produces, what a person writes, and how a source becomes a set of skills. Rules:
`SOURCE-02`, `COV-04`, `SIZE-01`, `COUNT-01`.

## Two kinds of content, two methods

| Content | Method | Why |
|---|---|---|
| Fields, types, enums, parameters, status codes | **generated by a script** from the machine-readable source | a model paraphrases a type or drops a value silently |
| Conventions, rationale, gotchas, the order to do things in | **written by a person** from the prose pages | no schema states them |

The split is not a preference. `SOURCE-02` puts no model between a specification and a reference file,
because the failure it prevents is invisible: a plausible field name that never existed.

## What a script cannot get

The prose around a schema is where the load-bearing knowledge often sits: which parameter is required
only in combination with another, which endpoint needs a header its sibling does not, what the
recommended integration order is. Extract those by hand from the pages, and cite the page.

`octo-api` shows the shape: `ENDPOINTS.md` and `PRODUCT-SCHEMA.md` are generated with a stamp on line
1, while the asymmetry that `Accept-Language` is required on one endpoint and not the other is prose
in `SKILL.md`, because no schema says so.

## Splitting a source into skills

Group by **what a reader asks about together**, not by how the upstream organises its navigation. The
upstream's structure serves browsing; a skill serves one question.

- One skill per domain a request names: products, availability, bookings.
- Capabilities or extensions that only apply on top of a domain go in that domain's file, or in one
  skill per **group** where there are many.
- At most 12 model-visible skills, and fewer is better: two skills that always fire together spend
  two descriptions for one concept. `COUNT-01`

## The map and the territory

`SKILL.md` stays a map: purpose, the core model, the counts, and the reference map. Under 120 lines,
or 40 for a pure domain map. Everything a reader looks **up** rather than reads goes into a reference
file. `SIZE-01`

The test for a line in `SKILL.md`: would the agent need it before knowing which reference to open? If
not, it belongs in the reference.

## Counts are the completion criterion

Record what the source contains and check the result against it: 46 paths, 65 operations, 139
schemas, 254 capability fields. A count is checkable and exhaustive at once, which is what makes it a
better criterion than any adjective. Put the counts in `SKILL.md` so a stale extraction is visible
without running anything.

## Never compress by omission

Distillation removes redundancy of expression. It never removes a field, an enum value, a default, an
error or a caveat. Where the upstream is silent on a facet, write that it is silent, because a blank
reads as absence and the reader cannot tell the two apart. `COV-04`

## Stamp what a script wrote

Line 1 of a generated file names the generator and the source hash, so a later hand edit is visible:

```markdown
<!-- generated by scripts/extract_spec.py from openapi.yaml sha256:d7bec97a — do not edit above the prose marker -->
```

A file that is part generated and part hand-written needs the marker, so the next run knows where to
stop overwriting. `SRC-03`
